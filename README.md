# Домашняя работа 2 — MongoDB

## Запуск

Нужны Docker с Compose v2. Все команды выполняются из папки с `compose.yaml`.

```sh
docker compose up -d
docker compose run --rm lab reset
docker compose run --rm lab fixtures
docker compose run --rm lab all
```

Отдельные сценарии:

```sh
docker compose run --rm lab data
docker compose run --rm lab index
docker compose run --rm lab purchase
docker compose run --rm lab failover
```

Сценарии сами готовят исходные данные; запускать их нужно последовательно. Фактические результаты автоматически сохраняются в `results/results.json` в Extended JSON. После изменения решения итоговый прогон выполняется повторно.

Для удобного просмотра сохранённых результатов используется `demo.js`:

```sh
docker compose run --rm -e DEMO_PART=data --entrypoint mongosh lab --nodb --quiet --file /work/demo.js
```

В `DEMO_PART` можно указать `summary`, `data`, `report`, `index`, `purchase`, `transactions`, `failover` или `all`. Режимы `plans` и `snapshots` показывают полные планы и снимки счётчиков. Скрипт читает `results/results.json`, выводит таблицы и JSON и проверяет соответствие результатов текущему решению. Опыты повторно не запускаются.

Остановка стенда с сохранением данных в Docker volumes:

```sh
docker compose down
```

## Окружение и использованные материалы

Использован выданный комплект `compose.yaml`, `lab.js`, `solution.js`; дополнительные примеры курса не использовались. Настройки окружения не менялись. Файлы проекта размещены в подпапке `project`.

MongoDB `8.0.30` работает в replica set `hw2rs` из трёх узлов: `m1:27017`, `m2:27017`, `m3:27017`. Базы — `hw2` и `hw2_failover`. Подключение выполняется внутри Docker-сети; порты на хост не опубликованы. Команды проверены в Windows через PowerShell.

В покупке используются предоставленные заданием оболочка `transaction` и фабрика ошибок `HWError`.

## 2. Модель данных и запросы

В `products` документ представляет товар; `_id` — его артикул, `variants` — размеры и остатки. В `orders` каждый заказ хранится отдельным документом, а `items[].sku` ссылается на `products._id`.

Позиции встроены в заказ, потому что относятся к одной покупке и читаются вместе. Они сохраняют состав покупки и цены. История покупателя хранится отдельными заказами: она растёт со временем, а отдельные документы позволяют фильтровать, сортировать и ограничивать выдачу без неограниченного массива внутри документа покупателя.

`items[].price` — цена единицы товара на момент покупки. Изменение текущей цены каталога не меняет стоимость прошлого заказа. Цены имеют тип Decimal128, дата заказа — BSON Date. При создании заказа количества и `userId` записываются как int32.

Валидатор `products` установлен через `collMod` в режиме `strict/error`. `$jsonSchema` проверяет обязательные поля, BSON-типы, структуру вариантов и неотрицательные цены и остатки. Дополнительный `$expr` запрещает повторяющиеся размеры. Служебные поля разрешены. Корректный документ принят; строковая цена и отрицательный остаток отклонены валидатором с кодом 121.

Поиск использует `$elemMatch`: размер и достаточный остаток должны относиться к одному варианту. Поэтому A с L = 0 и M = 10 не подходит для двух L; после изменения A/L на 2 подходит. Возвращаются полные товары со всеми вариантами, отсортированные по `_id`; используется `simple` collation.

История фильтруется по `userId` и `status`, сортируется по `{createdAt: -1, _id: 1}` и ограничивается 20 полными документами. `_id` задаёт однозначный порядок при одинаковых датах. Коллекции стенда создаются с `simple` collation по умолчанию. Проверены другой покупатель, другой статус и отсутствие совпадений.

## 3. Отчёт о продажах

Агрегация выбирает только `paid` за период `[from, to)`: начало включено, конец исключён. `$unwind` разворачивает позиции, `$group` объединяет размеры по SKU и считает количество и сумму `qty × items.price`. `$sort` упорядочивает по выручке по убыванию и SKU по возрастанию, `$limit` оставляет пять товаров. `$lookup` получает названия из `products`, `$project` формирует ответ. Выручка остаётся Decimal128.

Для периода `[2026-01-01T00:00:00Z, 2026-02-01T00:00:00Z)`:

| SKU | Название | Количество | Выручка |
|---|---|---:|---:|
| A | Футболка | 3 | 320.00 |
| B | Рубашка | 4 | 320.00 |
| C | Толстовка | 3 | 270.00 |
| D | Ремень | 2 | 240.00 |
| E | Сумка | 1 | 200.00 |

При равной выручке A идёт перед B по артикулу. F с выручкой 150.00 занимает шестое место.

Расчёт A по исходным заказам:

| Заказ | Размер | qty | Цена единицы | Стоимость |
|---|---|---:|---:|---:|
| sale-start | M | 2 | 100.00 | 200.00 |
| sale-middle | L | 1 | 120.00 | 120.00 |
| Итого | | 3 | | 320.00 |

Заказы `created` и `cancelled` исключены. Пустой период возвращает `[]`. После изменения цены A в каталоге на 999.00 отчёт остался прежним, поскольку выручка считается по историческим ценам позиций.

## 4. Индекс и план выполнения

Для запроса истории создан индекс:

```js
{userId: 1, status: 1, createdAt: -1, _id: 1}
```

Сначала стоят поля фильтра по равенству, затем поля сортировки. Внутри выбранных пользователя и статуса индекс упорядочен по дате по убыванию и `_id` по возрастанию. Последнее поле обеспечивает нужный порядок при одинаковых датах.

Оба плана получены через `explain("executionStats")` на одном наборе из 10 000 заказов для `userId: 2500, status: "paid"`, с лимитом 20:

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Есть отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10000 | Да |
| После индекса | 20 | 20 | 20 | Нет |

До индекса использовались `COLLSCAN` и отдельная `SORT`. После — `IXSCAN` без отдельной сортировки. Читаются также 20 полных документов: позиции и остальные поля заказа не покрыты индексом. Списки `_id` и их порядок совпали. `hint` не использовался.

Индекс занимает дополнительное место и требует обслуживания при вставке, удалении и изменении индексируемых полей.

## 5. Покупка и транзакция

Покупка выполняется через `c` одной транзакционной сессии:

1. Найти заказ с `_id = operationId`.
2. Если он существует, сравнить `userId`, длину и порядок позиций, значения `sku`, `size`, `qty`. При совпадении вернуть прежний заказ; при отличии — `REQUEST_CONFLICT`.
3. Для новой покупки последовательно списать оба товара. Фильтр `updateOne` содержит SKU и `$elemMatch` с размером и `stock >= qty`; `$inc` уменьшает остаток подходящего варианта.
4. После каждого обновления передать реальные `matchedCount` и `modifiedCount` в `trace`. При отсутствии товара, размера или достаточного остатка бросить `ITEM_UNAVAILABLE`.
5. Создать один заказ с `_id = operationId`, текущей датой, статусом `created` и ценами товаров, прочитанными в транзакции.

Оболочка использует `readPreference: primary`, `readConcern: snapshot` и `writeConcern: {w: "majority", j: true, wtimeout: 10000}`. Чтения выполняются из согласованного снимка. Успешное завершение тела приводит к commit, исключение из тела — к abort. Ошибка commit передаётся вызывающему коду и не объявляется успешным откатом. Автоматического повтора всей транзакции в оболочке нет.

Атомарность обеспечивает совместную фиксацию списаний и заказа либо отмену всех изменений покупки. Защита от повторного бизнес-запроса обеспечивается отдельно — сохранённым `operationId` и сравнением параметров. Новая транзакция сама по себе не запрещает повторно исполнить ту же покупку. Порядок ключей JSON и текущая цена каталога при сравнении не используются.

В опыте отката первое списание A/M действительно прошло (`modified: 1`), а второе для B/L не нашло достаточного остатка (`matched: 0`). После abort A/M снова 10, B/L снова 5, заказа нет, получена ошибка `ITEM_UNAVAILABLE`.

Успешная покупка уменьшила A/M до 8 и B/L до 4 и создала один заказ. Повтор вернул ту же дату и цены 100.00 и 80.00 без новых списаний, хотя текущая цена A уже была изменена на 777.00. Изменённое количество с прежним `operationId` дало `REQUEST_CONFLICT` без изменения данных.

Для каждого из двух опытов сохранены отдельные полные снимки `serverStatus().transactions` до и после и метаданные `host`, `pid`, `localTime`, `uptime`. Снимки сняты вне транзакционной сессии с одного процесса, без других транзакций и переключения primary между измерениями.

| Опыт | Δ totalStarted | Δ totalCommitted | Δ totalAborted |
|---|---:|---:|---:|
| Успех | 1 | 1 | 0 |
| Откат | 1 | 0 | 1 |

Повторных попыток в этих измерениях не было. Счётчики общие для процесса и дополняют `trace` и сравнение состояний, но сами по себе не доказывают атомарность. Для повтора подтверждённой покупки нулевая разность не требуется.

## 6. Смена primary

Контрольная запись выполняется с `writeConcern: {w: "majority", j: true, wtimeout: 10000}`. `upsert: true` делает повтор с теми же ID и сообщением безопасным при потере ответа.

В сохранённом опыте роли изменились так:

| Узел | До | После |
|---|---|---|
| m1:27017 | PRIMARY | SECONDARY |
| m2:27017 | SECONDARY | SECONDARY |
| m3:27017 | SECONDARY | PRIMARY |

Первая majority-запись подтверждена. После `replSetStepDown` тем же экземпляром клиента прочитан прежний документ и подтверждена новая запись. Оба документа присутствуют.

Клиент подключён по списку адресов с `replicaSet=hw2rs`, отслеживает топологию replica set и направляет операции на актуальный primary. Ручная смена адреса и создание нового клиента не нужны. При временной ошибке сценарий повторяет операции после готовности нового primary.

Majority означает подтверждение большинством, а не всеми узлами. Отдельная secondary может отставать, поэтому чтение с любой secondary не обязано немедленно увидеть подтверждённую запись. В опыте используется `readPreference: primary`.

## 7. Шардирование

При ключе `{userId: 1}` значения меньше 2000 находятся на A, диапазон `[2000, 5000)` — на B, значения от 5000 — снова на A.

- История `{userId: 2500}` направляется только на B: значение ключа попадает в его диапазон.
- Общий отчёт `{status: "paid"}` опрашивает A и B: фильтр не ограничивает `userId`, подходящие документы могут находиться на обоих шардах.
- Локальный индекс `{status: 1}` не меняет число участников: общий отчёт по-прежнему идёт на A и B. Индекс может сократить локальный просмотр документов при выборе его оптимизатором. Маршрутизацию определяют ключ шардирования и карта диапазонов.
